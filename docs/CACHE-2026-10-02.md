# HTML caching: root cause and target architecture (2026-10-02)

Follows `docs/CACHE-2026-10-01.md` (layers, measurements, the stale-page guard). Theme 1.2.19, Core 1.2.16.

## 1. Root cause
**The host's edge** (Cloudflare in front of GoDaddy Managed WordPress) applies "Cache Everything". It also **replaces every HTML response's `Cache-Control` with `public, max-age=2678400` (31 days)**. A browser then reuses its copy of a page for 31 days without asking.

No WordPress header can change this: the edge overwrites it. The setting belongs to GoDaddy's Cloudflare zone, and the owner has no direct access to it.

## 2. What a 31-day copy can make stale, and what limits it
| Item | Can a visitor see it stale? | Limit today |
|---|---|---|
| HTML text, menus, footer, offers | yes, up to 31 days after their last full load | the guard reloads the page once it sees a newer build or content epoch (immediately when the page's id is not the last one seen, otherwise within 30 min) |
| SEO metadata (title, description, canonical, hreflang, JSON-LD, robots) | **for browsers: yes**, but browsers don't use it. **For crawlers:** they get the edge copy, which "Flush Cache" purges and saves refresh | crawlers don't keep a 31-day browser cache; indexing is off anyway |
| Theme version, CSS/JS references | an old page references old `?ver=` URLs. If the edge has dropped them, the origin serves the **current** file under the old URL (old markup + new code) | the guard (pages since 1.2.15); the assistant script reloads pages that carry no build id (1.2.17); components tolerate missing markup |
| Assistant code | loaded on demand by the page's loader with the page's `?ver=` | same as above |
| Pages cached before 1.2.15 | yes, with no guard | they expire by about 29 October 2026 |

## 3. Target architecture
| Layer | Target | Status |
|---|---|---|
| Fingerprinted static assets (CSS, JS, fonts, images; `?ver=<mtime>`) | long caching (immutable in practice) | **in place**. A deploy changes the URL. The CSS bundle (1.2.19) is versioned the same way. |
| HTML at the browser | `no-cache` (revalidate each visit) or a short TTL (≤ 10 min) | **owner + GoDaddy:** ask GoDaddy support to set the zone's Browser Cache TTL for HTML to "Respect Existing Headers". Then ship the one-line Core change that sends `Cache-Control: no-cache, max-age=0` for anonymous HTML. Not before: today it would be overwritten, and if a layer started honouring it unannounced, edge caching could drop. |
| HTML at the edge | cached, purged on change | in place: "Flush Cache" purges it, and content saves purge it |
| Deploy invalidation | every deploy purges the host cache | **owner decision.** GoDaddy documents `wp wpaas cache flush` (object and Varnish cache). Adding it to the deploy workflow is a write action on production, and adding that step was refused in this session. The owner can either add the step, or keep flushing from the WP admin bar after each deploy. |
| Deploy verification | the edge copy of `/` carries the live build id | **added** (deploy workflow, warning only): it compares `/`'s `er-build` with `/wp-json/egypt-roamer/v1/build` |
| Defence in depth | the stale-page guard | kept, unchanged (verified end to end on production on 1 Oct) |

The flush step, for the owner to add after the public-page health check:
```yaml
      - name: Flush the host page cache
        env: { SSH_USER: ${{ secrets.PROD_SSH_USER }}, SSHPASS: ${{ secrets.PROD_SSH_PASSWORD }} }
        run: sshpass -e ssh $SSH_OPTS "$SSH_USER@$SSH_HOST" 'cd "$HOME/html" && wp wpaas cache flush'
```
GoDaddy's documentation doesn't say whether this command also purges the Cloudflare edge. The new build-id check shows whether it does on the first deploy.

## 4. What is predictable today
After a deploy **and** a flush:
- new visitors get the new pages at once;
- a returning visitor with a 31-day copy gets one automatic reload on their next visit (≤ 30 minutes for content changes).

Without the flush, each visitor's first stale page costs one extra uncached load (`?nocache=`), and pages are still correct.
