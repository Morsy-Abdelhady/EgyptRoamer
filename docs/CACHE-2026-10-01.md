# HTML caching: the 31-day browser copy and the stale-HTML guard (2026-10-01)

Launch-gate item O2. Theme 1.2.15, Core 1.2.14.

## 1. The layers, measured on production
| Layer | Behaviour | Evidence |
|---|---|---|
| **Browser** | Keeps each page for **31 days** (`Cache-Control: public, max-age=2678400`, `Expires` +31 days, `Last-Modified`, no ETag). During that time it shows its copy **without asking the server**. | Production headers on 2026-10-01: `/` MISS → `max-age=2678400`. A browser that had visited on 28 Sep still showed the **theme 1.2.7** homepage (no Trip assistant) on 1 Oct, after five deploys and two flushes. |
| **Cloudflare edge** (GoDaddy's CDN) | Caches every page ("Cache Everything + Edge TTL") and **replaces** WordPress's `Cache-Control` with the 31-day one. No WordPress response header can change this. Flushed by GoDaddy's "Flush Cache", and on content saves. | `cf-cache-status` MISS then HIT; WordPress's `no-store` is replaced (27 Sep, `docs/LAUNCH-GATE.md`, affiliate redirect architecture). |
| **Edge bypass** | `wp-admin`, `wp-login`, `wp-json`, … paths; logged-in cookies; a query string **starting with** `nocache` | `/?nocache=…` → `DYNAMIC`, no Cache-Control; `/wp-json/` → `DYNAMIC`; but `style.css?nocache=…` → MISS and cached (static files are not bypassed) |
| **GoDaddy gateway** | Behind the edge (`x-gateway-cache-status`); follows the same purge | headers |
| **WordPress** | Sends no caching header for anonymous pages; no page-cache plugin | code |
| **Assets** | CSS and JS are versioned (`?ver=<file mtime>`), so a new deploy gives new URLs. Long caching is right for them and is kept. | `er_asset_ver()` |

**What goes wrong:**
1. **A returning visitor can see a page up to 31 days old**, after any number of deploys, flushes or content changes, until they reload.
2. **Old HTML can run new code.** When the edge copy of an asset under an old `?ver=` expires, the origin serves the **current** file under the old URL: old markup plus new JS. Today's components tolerate missing markup, but this is a latent class of bugs.

## 2. Fix in the site (no host change needed): the stale-HTML guard
- **Build id.** Every page carries `<meta name="er-build">`: a 12-character hash of the Core and theme versions, the asset versions, and a **content epoch**. The epoch changes when an editor saves visible content (public post types, offers, providers, menus, Polylang strings, Egypt Roamer settings and homepage options). It does **not** change on visitor submissions, counters or rate limits.
- **The check.** `GET /wp-json/egypt-roamer/v1/build` (edge-bypassed, `no-store`) returns the current id. A 0.7 KB inline script in `<head>` asks for it:
  - **at once** when the page's id is not the last current id this browser saw;
  - **otherwise at most every 30 minutes** per browser. That's the load cost: about one light WordPress request per visitor per half hour.
- **Stale page:**
  1. `location.reload()` once: the browser revalidates, and after a flush the edge has the new page.
  2. If it's still stale (the edge wasn't flushed): one load with `?nocache=<build>` **as the first query parameter** (the edge's bypass rule), then `history.replaceState` removes it from the address bar.
  3. A session marker prevents any loop. If the check fails (offline or a server error), nothing happens.
- **Kept as it is:** static asset caching (versioned URLs), the edge cache, and Cloudflare protection.

**Limits:**
- **Copies cached before this release** have no guard. They expire on their own by about 29 October 2026, or on a manual reload.
- **Editor changes** reach a browser that checked within the last 30 minutes at its next check.
- **Without a flush after a deploy**, each visitor's first stale page costs one extra uncached load; pages are correct either way. So the flush after a deploy still matters (see 3).

## 3. Recommended host-side settings (owner, GoDaddy support)
1. **Browser cache TTL for HTML:** ask GoDaddy to stop overriding it for HTML, or set it short. Cloudflare "Browser Cache TTL: Respect Existing Headers"; WordPress would then need to send `Cache-Control: no-cache` for HTML, so browsers revalidate on each visit. That's a one-line Core change, made together with the host change and not before: today the edge replaces it anyway, and if a host layer started honouring it unannounced, edge caching could drop. The edge can keep its own TTL, because it's purged.
2. **Purge on deploy:** add GoDaddy's cache flush to the deploy workflow if GoDaddy offers a CLI or API for it. Today the deploy workflow is read-only on the server by design, and the flush is done in the WP admin bar ("GoDaddy Quick Links → Flush Cache").

|---|---|

| B. another page within 30 min | no request |
| C. stale browser copy, current edge | exactly one reload, then the current page |
| D. stale edge too | reload, then one `?nocache=` load; address bar clean |
| E. stale search page | `/?nocache=…&s=cairo`; query kept |
| F. after an editor's change (a browser that last checked over 30 min ago) | one reload, new build |
| G. the build check fails | no reload, no loop |
